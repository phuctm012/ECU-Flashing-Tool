v1.1 — Setup & Debug Guide (Real ECU, Windows)

A. Setup môi trường trên máy Windows mới

Phần cứng Vector (VN1640A/VN1630) chỉ chạy được trên Windows — XL Driver Library không có bản macOS/Linux. Nên chạy mọi thứ qua terminal/PowerShell, không double-click file — nếu app crash, traceback đầy đủ sẽ hiện ra terminal thay vì biến mất cùng cửa sổ.

1. Cài Python + lấy code

# Cài Miniforge/conda nếu máy chưa có: https://github.com/conda-forge/miniforge

git clone https://github.com/phuctm012/ECU-Flashing-Tool.git
cd ECU-Flashing-Tool

conda create -n pyside6 python=3.12
conda activate pyside6

2. Cài dependencies (bao gồm python-can cho hardware thật)

pip install -r requirements.txt
pip install python-can

3. Cài Vector Driver Setup

Tải từ vector.com — hoặc đã có sẵn nếu máy từng cài CANoe/CANalyzer/CANape. Gói này cài 2 thứ cần thiết:

  • XL Driver Library — thư viện driver mà python-can dùng để giao tiếp phần cứng.
  • Vector Hardware Config (tên cũ: Vector Hardware Manager) — bắt buộc dùng ở mục B bên dưới.

4. Cắm hardware

Cắm VN1640A/VN1630 vào máy qua USB. Windows tự nhận driver nếu Vector Driver Setup đã cài xong.

B. Cấu hình Vector Hardware Config (bắt buộc)

Quan trọng: đây là bước hay bị bỏ sót nhất và là nguyên nhân phổ biến nhất khiến kết nối thất bại dù hardware đã cắm vào máy và Windows đã nhận driver. Vector XL Driver không cho ứng dụng truy cập channel tự do — mỗi phần mềm phải được đăng ký tên ứng dụng, và channel vật lý phải được gán (assign) cho đúng tên đó. Tool này đăng ký với tên FlashTool (xem communication/vector_can.py, tham số app_name).
  1. Mở Vector Hardware Config (tìm trong Start Menu sau khi cài Driver Setup).
  2. Vào tab Applications → nếu chưa có mục "FlashTool", bấm Add/New Application để thêm — đặt tên đúng chính xác FlashTool (phân biệt hoa/thường).
  3. Ở mục cấu hình của "FlashTool", kéo/gán (assign) channel vật lý muốn dùng vào đó — ví dụ kéo "VN1640A – Channel 1" vào slot CAN1 của ứng dụng FlashTool.
  4. Save lại cấu hình.
Vì sao "thấy" hardware mà vẫn không kết nối được: lệnh python cli.py list-hardware (hoặc nút Refresh trong GUI) chỉ hỏi driver "có hardware nào cắm vào máy" — bước quét này không cần đăng ký app. Nhưng bước kết nối thật (Test Connection / Flash) thì driver bắt buộc phải tra kênh theo tên app đã đăng ký ở bước B — nếu chưa gán, sẽ báo lỗi ngay khi bắt đầu kết nối chứ không phải lúc quét.

C. Nếu máy có cài CANoe/CANalyzer song song

  • CANoe và FFlash có thể cùng đăng ký dùng chung 1 channel vật lý (driver Vector hỗ trợ nhiều app/channel).
  • Nên dừng measurement (hoặc đóng hẳn) CANoe trong lúc dùng FFlash, tránh 2 bên cùng gửi frame lên bus gây xung đột/nhiễu trace — đặc biệt nếu CANoe có node giả lập gửi UDS/TesterPresent trùng CAN ID.
  • Nếu chỉ dùng CANoe để log CAN bus song song (không có node nào chủ động gửi UDS): về nguyên tắc chạy cùng lúc được, nhưng nhớ tắt TesterPresent tự động của CANoe trên đúng CAN ID của ECU đang flash — nếu cả 2 bên cùng gửi TesterPresent (0x3E), ECU có thể raise NRC bất thường hoặc rớt session giữa chừng.
App tự cảnh báo: trước khi flash vào hardware thật (không áp dụng cho Virtual ECU Simulator), FFlash tự kiểm tra 2 tín hiệu — tiến trình CANoe.exe/CANalyzer.exe/ CANape.exe đang chạy (qua tasklist), và channel đang chọn có báo is_on_bus (đã có app khác giữ) hay không. Trong GUI hiện hộp thoại Yes/No (mặc định No); trong CLI chỉ in cảnh báo ra stderr rồi tiếp tục chạy (không chặn script).

D. Tự kiểm tra môi trường trước (test suite ảo, không cần hardware)

Trước khi đụng tới ECU thật, chạy toàn bộ test suite tự động — mọi test đều chạy qua Virtual ECU Simulator, không cần hardware cắm vào máy. Nếu bộ này không pass 100% trên máy Windows mới, môi trường/dependency đang có vấn đề — dừng lại xử lý trước khi thử với ECU thật, đừng cố flash thật trên một môi trường chưa xác nhận chạy đúng.

conda activate pyside6
python -m unittest discover -s tests -p "test_*.py" -v

# Kỳ vọng: dòng cuối "OK", không có FAILED/ERROR

Nếu lỗi ngay ở bước import/collection (chưa chạy tới test nào) — thường là thiếu PySide6/python-can hoặc sai Python version. Kiểm tra lại mục A.

E. Quy trình test an toàn trên ECU thật (theo đúng thứ tự)

Không nhảy cóc bước. Mỗi bước dưới đây an toàn hơn bước sau — dừng lại và xử lý lỗi ngay khi 1 bước không như mong đợi, đừng chạy tiếp bước tiếp theo "cho thử". Nếu có ECU dự phòng/bench, luôn test trên đó trước khi đụng tới ECU sản xuất/xe thật.

1Xác nhận hardware đã được nhận diện đúng

python cli.py list-hardware

Kỳ vọng: thấy đúng channel VN1640A/VN1630 đã gán ở mục B, không phải danh sách rỗng.

2Xem thông tin file firmware (không đụng ECU)

python cli.py info firmware.s3

3Xem trước sequence sẽ chạy — KHÔNG gửi gì tới ECU

python cli.py flash firmware.s3 --sequence suzuki --dry-run

Kiểm tra logic/thứ tự bước đúng trước khi cho phép tool thật sự gửi frame lên bus.

4Test kết nối + Security Access — an toàn, KHÔNG Erase/Download

python cli.py test-connection --hardware vector --channel 0 --sequence suzuki --verbose

Chỉ thực hiện Session Control + Security Access (+ đọc ECU Identification, read-only) — không bao giờ đụng Erase Memory/TransferData. Luôn tự khôi phục ECU về Default Session khi kết thúc, dù pass hay fail giữa chừng. Kết quả in PASSED (exit code 0) hoặc FAILED kèm lý do cụ thể (exit code 1) — ví dụ NRC 0x35 (Invalid Key) nghĩa là thuật toán/DLL security chưa đúng (xem mục F).

Cũng có trên GUI: menu Tools → Test Connection..., cùng logic, hiện kết quả trong 1 dialog nhỏ.

5Chỉ khi bước 4 PASSED mới flash thật

python cli.py flash firmware.s3 --hardware vector --channel 0 --sequence suzuki --verbose > flash_log.txt 2>&1

--verbose > flash_log.txt 2>&1 gộp cả stdout + stderr vào 1 file, có đầy đủ TX/RX hex frame — giữ lại file này (xem mục G nếu cần gửi debug).

Tương đương qua GUI (python main.py): Configure → Communication → bấm Refresh → chọn channel thật vừa xuất hiện → chọn Radar Side đúng ECU → Configure → Data → nạp firmware → Tools → Test Connection... (bước 4) → Flash tab → Flash (bước 5).

F. Radar Side / Security DLL — cấu hình theo ECU thực tế

Radar Side (Suzuki SLP1 sequence)

Radar SidePhysical Request CAN IDResponse CAN ID
S0 (mặc định)0x77B0x78B
S10x77A0x78A

Chọn đúng Radar Side khớp với ECU vật lý đang flash (combo Radar Side trong GUI, hoặc --radar-side {s0,s1} trong CLI) — sai Radar Side nghĩa là gửi UDS request tới sai CAN ID, ECU sẽ không phản hồi gì cả (timeout), không phải một lỗi rõ ràng.

Security Access DLL (nếu ECU dùng thuật toán OEM riêng)

Thứ tự ưu tiên tính key bảo mật: key_function truyền thẳng (không dùng trong GUI/CLI thông thường) → Security DLL đã load → thuật toán "dummy" mặc định của Virtual ECU Simulator (chỉ dùng được với ECU giả lập, không hoạt động trên ECU thật có bảo mật thật).

Nếu ECU yêu cầu thuật toán riêng: chọn file DLL ở mục Security Access DLL (Browse... trong GUI), hoặc --security-dll <path> trong CLI. DLL phải export đúng hàm:

// C signature mong đợi trong DLL
UINT32 GenerateKeyEx(UINT32 seed);

Tool load DLL qua ctypes.CDLL, gọi hàm GenerateKeyEx (mặc định — có thể đổi tên hàm qua tham số riêng nếu cần) với seed nhận từ ECU, kỳ vọng nhận lại key dạng UINT32.

G. Cách lấy log gửi lại để debug

Khi gặp lỗi, gửi lại càng nhiều trong số dưới đây càng tốt — đặc biệt là trace CSV (cho biết chính xác frame nào ECU không phản hồi đúng) và log verbose (cho biết chính xác bước nào raise exception).

NguồnCách lấyKhi nào ưu tiên
Trace CSV (GUI) Tab Trace → chuột phải → "Save Log (CSV)..." Ưu tiên cao nhất — đúng format 6 cột (Request/Response Timestamp, Target/Source, Data) giống docs/*_Report_Trace.csv đã dùng để đối chiếu byte-level trước đó, đối chiếu trực tiếp từng bước UDS được ngay.
CLI verbose log --verbose > flash_log.txt 2>&1 (xem mục E, bước 4/5) Gộp stdout + stderr, có đầy đủ TX/RX hex frame + traceback nếu crash — dùng khi chạy qua CLI (không cần GUI mở).
Information log (GUI) Tab Information → chuột phải → "Save Log..." (.txt) Log dễ đọc hơn, bổ trợ cho Trace CSV — tốt để hiểu nhanh "chuyện gì đã xảy ra" trước khi đọc trace chi tiết.
Export Report (GUI) Menu Tools → Export Report... 1 file HTML tổng hợp cả session (ECU info, checksum, từng bước, trace) — tiện nếu chỉ muốn gửi 1 file duy nhất thay vì nhiều file rời.
Traceback khi crash Copy nguyên văn từ terminal/PowerShell Chỉ thấy được nếu chạy qua terminal (mục A) — double-click .exe/file .py sẽ làm cửa sổ đóng lại và mất traceback ngay khi crash.
Khi gửi lại để debug, kèm theo: (1) file log/trace theo bảng trên, (2) mô tả ngắn gọn đang làm gì (đúng lệnh CLI đã chạy, hoặc đang bấm nút gì trong GUI), (3) kết quả mong đợi vs. thực tế xảy ra, (4) đã làm tới bước nào trong mục E (an toàn tới đâu, có PASSED bước 4 chưa).

I. Checklist tóm tắt (in ra để cạnh máy)

  • Đã git clone + tạo conda env + pip install -r requirements.txt + pip install python-can
  • Đã cài Vector Driver Setup (XL Driver Library + Vector Hardware Config)
  • Đã cắm VN1640A/VN1630 qua USB
  • Vector Hardware Config: đã thêm app FlashTool và gán đúng channel vật lý, đã Save
  • Nếu có CANoe: đã đóng/dừng measurement trước khi chạy FFlash
  • python -m unittest discover -s tests -p "test_*.py" -v → OK, không lỗi
  • python cli.py list-hardware → thấy đúng channel mong đợi
  • python cli.py flash firmware.s3 --sequence suzuki --dry-run → sequence đúng
  • python cli.py test-connection --hardware vector --channel 0 --sequence suzuki --verbose → PASSED
  • Chỉ sau khi PASSED mới chạy flash thật, luôn kèm --verbose > flash_log.txt 2>&1
  • Nếu có lỗi: đã lưu Trace CSV + log verbose + mô tả ngắn gọn để gửi lại debug (mục G)
